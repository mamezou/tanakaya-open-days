# 要件定義書：田中屋 営業日カレンダー

状態：確定（2026-10-05）

## はじめに

ヴィーガンラーメン店「田中屋」の営業日を1つの設定ファイルで管理し、公開ページとLINEの前日配信に自動で反映する。元資料は `docs/plan.md` の3〜6章。

範囲外：

- 管理画面（Cognito、カレンダーでの登録、本アプリからの訂正配信）
- Instagram用の素材生成と自動投稿
- 独自ドメイン、予約受付、売上管理
- 祝日の扱い（祝日による営業・休業の判定）。祝日に営業や休業をするときは、例外として登録する
- LINEの月の通数の上限を見越した送信の制御（上限で送信が失敗した日は、失敗として記録する）

受け入れ基準は EARS の形（WHEN / IF / WHILE ... THEN ... SHALL）で書く。末尾の「正しさの性質」は、プロパティベーステストで1つずつ検証する。

## 用語

| 用語 | 意味 |
|---|---|
| 判定機能 | 日付1日について「営業」か「休業」を返す純粋関数 |
| 営業曜日 | 設定ファイルで指定する、既定で営業する曜日。田中屋は日曜だけ |
| 既定の営業日 | 曜日が営業曜日に含まれる日 |
| 例外 | 設定ファイルに登録した休業日または臨時営業日 |
| 設定ファイル | `data/settings.json`。git では管理しない。見本は `data/settings.example.json` |
| 公開用データ | デプロイ時に設定ファイルから作る JSON |
| 配信処理 | 前日配信を行う Lambda 関数 |
| 対象日 | 配信処理の実行時刻を日本時間にした日付の翌日 |
| 配信記録 | 対象日ごとの配信の状態を残す DynamoDB の項目 |

## 共通の制約

- 日付は日本時間（Asia/Tokyo）の暦日として `YYYY-MM-DD` で扱い、実行環境のタイムゾーンに依存しない
- 判定機能、対象日の計算、公開用データの生成は、現在時刻を引数で受け取る純粋関数とする
- AWS のリソースは AWS SAM で定義し、東京リージョンにデプロイする。Lambda のランタイムは `nodejs24.x`

## 要件

### 要件1：営業日の判定

**ユーザーストーリー：** お客様として、田中屋がある日に営業しているかを知りたい。無駄足を踏まないため。

#### 受け入れ基準

1. 判定機能 SHALL 日付、営業曜日、例外を入力として受け取り、「営業」または「休業」と、例外による結果かどうかを返す
2. WHEN 日付に例外がない THEN 判定機能 SHALL その日の曜日が営業曜日に含まれれば営業、含まれなければ休業と判定する
3. WHEN 日付が休業日に登録されている THEN 判定機能 SHALL 休業と判定する
4. WHEN 日付が臨時営業日に登録されている THEN 判定機能 SHALL 営業と判定する
5. 判定機能 SHALL 営業曜日をコードに固定せず、設定ファイルの値を使う

### 要件2：設定ファイル

**ユーザーストーリー：** 運用者として、営業曜日、休業日、営業時間を1つのファイルで管理したい。提出後のコミット禁止期間にも、デプロイだけで変更を反映するため。

#### 受け入れ基準

1. 設定ファイル SHALL 営業曜日、休業日の一覧、臨時営業日の一覧、営業時間（開始と終了）、前日配信の時刻だけを持つ
2. IF 設定ファイルがない、または JSON として読めない THEN システム SHALL デプロイを失敗させる
3. IF 営業曜日が、曜日の名前（`sun`〜`sat`）を重複なく1つ以上並べたものでない THEN システム SHALL デプロイを失敗させる
4. IF 日付が `YYYY-MM-DD` の実在する日でない THEN システム SHALL デプロイを失敗させる
5. IF 同じ日付が休業日と臨時営業日の両方にある THEN システム SHALL デプロイを失敗させる
6. IF 休業日が既定の営業日でない、または臨時営業日が既定の営業日である THEN システム SHALL デプロイを失敗させる
7. IF 時刻が `HH:MM`（24時間制）でない、または営業時間の開始が終了より後か同じ THEN システム SHALL デプロイを失敗させる
8. IF 定義していない項目（メモなど）がある THEN システム SHALL デプロイを失敗させる
9. WHEN デプロイを失敗させる THEN システム SHALL 違反した項目と理由をすべて表示する
10. 見本ファイル `data/settings.example.json` SHALL 営業曜日を日曜だけとし、設定の検証を通る

### 要件3：公開用データの生成

**ユーザーストーリー：** 運用者として、デプロイすれば公開ページが新しい設定で表示されてほしい。手作業の更新をなくすため。

#### 受け入れ基準

1. WHEN デプロイする THEN システム SHALL 設定ファイルから公開用データを生成する
2. 公開用データ SHALL デプロイ日の属する月の1日から、11か月後の月末までの各日を含む
3. 公開用データの各日の営業可否と例外による結果かどうか SHALL 判定機能の結果と一致する
4. 公開用データ SHALL 各日の日付、営業可否、例外による結果かどうかと、営業時間、対象範囲、生成日時だけを含む
5. 公開用データ SHALL 配信記録、トークン、AWS のリソース名を含まない
6. WHEN デプロイが終わる THEN 公開ページ SHALL 新しい公開用データを表示する（CloudFront のキャッシュの無効化を含む）

### 要件4：公開ページ

**ユーザーストーリー：** お客様として、スマートフォンで今日と今月・来月の営業日を確かめたい。来店の予定を立てるため。

#### 受け入れ基準

1. 公開ページ SHALL Amazon S3 に置き、Amazon CloudFront の既定ドメインで配信する。S3 バケットは直接公開しない
2. WHEN ページを開く THEN 公開ページ SHALL 閲覧者の端末時刻を日本時間にした日付を「今日」として、その日の営業可否と、営業する場合は営業時間を表示する
3. 公開ページ SHALL 「今日」の属する月と翌月の営業カレンダーを表示し、例外による営業・休業を区別して示す
4. WHEN 再デプロイなしで日付や月が変わった後にページを開く THEN 公開ページ SHALL 新しい「今日」に合わせて表示する
5. IF 「今日」が公開用データの範囲外にある THEN 公開ページ SHALL 営業可否を表示せず、公式LINEで確かめるよう案内する
6. 公開ページ SHALL 公式LINEの友だち追加リンク（https://lin.ee/OReUh6e）と Instagram（https://instagram.com/tanakaya_ramen）へのリンクを置く
7. 公開ページ SHALL 営業可否を色だけでなく文字でも示し、カレンダーを見出し付きの表として読み上げられる形にする
8. 公開ページ SHALL 幅 360px の画面で横スクロールなしに読める

### 要件5：前日配信

**ユーザーストーリー：** お客様として、翌日の営業をLINEで前日に知りたい。臨時休業に気づかず来店しないため。

#### 受け入れ基準

1. システム SHALL 毎日、設定ファイルの配信時刻（日本時間）に Amazon EventBridge Scheduler で配信処理を起動する
2. 配信処理 SHALL 対象日を、実行時刻を日本時間にした日付の翌日とする
3. WHEN 対象日が既定の営業日で例外がない THEN 配信処理 SHALL 通常営業の案内を、LINE公式アカウントの友だち全員へ送る
4. WHEN 対象日が休業日に登録されている THEN 配信処理 SHALL 臨時休業の案内を友だち全員へ送る
5. WHEN 対象日が臨時営業日に登録されている THEN 配信処理 SHALL 臨時営業の案内を友だち全員へ送る
6. WHEN 対象日が既定の営業日でなく例外もない THEN 配信処理 SHALL 送らない
7. 案内の文面 SHALL 対象日の月日と曜日、案内の種類、田中屋のホームページの URL を含む。営業する案内（通常営業・臨時営業） SHALL 営業時間、予約の方法、Instagram の URL も含む
8. 配信処理 SHALL 最後にデプロイした設定で判定する
9. 配信処理 SHALL LINE Messaging API の broadcast で送る

### 要件6：二重配信の防止

**ユーザーストーリー：** お客様として、同じ案内を何度も受け取りたくない。運用者として、通数を無駄にしたくない。

#### 受け入れ基準

1. 配信処理 SHALL 同じ対象日への自動配信を最大1回とする
2. WHEN 送る前 THEN 配信処理 SHALL 対象日の配信記録を、同じ対象日の記録がない場合だけ作る条件付き書き込みで作る
3. IF 対象日の配信記録がすでにある THEN 配信処理 SHALL 送らずに終わる
4. IF 送信 API がエラーを返した（月の通数の上限を超えた場合を含む）、またはタイムアウトした THEN 配信処理 SHALL 再送せず、配信記録を「失敗」にしてエラーをログに残す
5. WHEN 配信後に設定を変えて再デプロイする THEN システム SHALL 同じ対象日には再配信しない（訂正は LINE Official Account Manager から手で送る）
6. 配信記録 SHALL 対象日、状態（送信中・送信済み・失敗）、案内の種類、記録日時を持つ

### 要件7：配信の安全

**ユーザーストーリー：** 運用者として、テストや設定の誤りで実際のお客様に配信したくない。LINEの配信は取り消せないため。

#### 受け入れ基準

1. 配信処理 SHALL チャネルアクセストークンを実行時に SSM Parameter Store の SecureString から読み、ログ、エラーメッセージ、配信記録に含めない
2. システム SHALL 読む SSM パラメータの名前をデプロイのパラメータで受け取る（テスト用アカウントと本番アカウントを切り替えるため）
3. システム SHALL 配信の有効・無効をデプロイのパラメータで受け取り、既定を無効とする。WHILE 無効 THEN EventBridge Scheduler SHALL 配信処理を起動しない
4. システム SHALL Webhook の受信口を作らない

## 正しさの性質

プロパティベーステストで検証する。P1〜P7 は `docs/plan.md` 5.2 の性質、P8 と P9 は追加の性質。「どの設定でも」は、要件2の検証を通る任意の設定（営業曜日も任意）を指す。生成器の範囲は `.kiro/steering/testing.md` に従う。

| No. | 性質 | 要件 |
|---|---|---|
| P1 | 休業日に登録した日は、どの設定でも休業と判定される | 1.3 |
| P2 | 臨時営業日に登録した日は、どの設定でも営業と判定される | 1.4 |
| P3 | 例外がない日は、曜日が営業曜日に含まれるときだけ営業と判定される | 1.2、1.5 |
| P4 | 有効な設定に例外を1つ加え、それを削除すると、すべての日の判定が加える前と一致する | 1.2〜1.4 |
| P5 | 同じ対象日について配信処理を何回実行しても（並行実行を含む）、LINE への送信は1回以下になる | 6.1〜6.3 |
| P6 | 任意の実行時刻について、対象日は実行時刻を日本時間にした日付の翌日になる（月末、年末、うるう日、日本時間の0時前後を含む） | 5.2 |
| P7 | 公開用データの各日の営業可否と例外による結果かどうかは、判定機能の結果と一致する | 3.3 |
| P8 | 公開用データの範囲内の任意の閲覧時刻について、公開ページが「今日」として表示する内容は、閲覧時刻を日本時間にした日付の判定と一致する | 4.2、4.4 |
| P9 | 設定の検証は、規則を満たす設定をすべて受け入れ、不正な営業曜日、休業日と臨時営業日の両方に入る日、効果のない例外のいずれかを含む設定をすべて拒否する | 2.3、2.5、2.6 |
